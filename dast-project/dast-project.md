## Проект. Оркестратор фаззинг-тестирования

В dast-1 и dast-2 мы запускали AFLplusplus вручную. Теперь напишем небольшое CLI-приложение, которое будет собирать проект, запускать фаззинг с настройками из YAML/TOML и сохранять результаты. Язык реализации можно выбрать самостоятельно.

### Общая часть

Реализуйте запуск одной командой, например:

```shell
python -m dast_project fuzz config.toml
```

В конфигурации задаются каталог проекта, команды сборки, параметры фаззинга и каталог результатов. Пример:

```toml
work_dir = "./cppcheck"
output_dir = "./submission/artifacts/cppcheck"
build_command = """
  CC=afl-clang-lto CXX=afl-clang-lto++ cmake -S . -B build-afl
  cmake --build build-afl --clean-first -j2
"""

[fuzzing]
command = ["./build-afl/bin/cppcheck", "@@"]
input = "./input"
dictionary = "./dictionary.dict"
duration_seconds = 300
```

Пути `work_dir`, `output_dir`, `input` и `dictionary` считайте относительно файла конфигурации. Команду исследуемой программы выполняйте в `work_dir`.

Приложение должно:

- Выполнять `build_command` в `work_dir` с остановкой при первой ошибке и сохранять журнал `logs/build.txt`.
- Запускать AFLplusplus с указанными корпусом, словарём и командой программы.
- Корректно завершать фаззинг по истечении `duration_seconds`, сохраняя весь каталог `out/`. Существующие результаты не перезаписывать.
- Сообщать об ошибочном TOML/YAML, отсутствии программы или входных файлов, ошибке сборки и запуска фаззера.
- Сохранять `summary.json`: команды, статус запуска, фактическую длительность, пути к артефактам, статистику из `fuzzer_stats` и результаты своего варианта.

### Варианты

Выполните **один назначенный вариант**.

1. **Сравнение корпуса и словаря.** Добавьте запуск трёх конфигураций: один входной пример без словаря; подготовленный корпус без словаря; тот же корпус со словарём. Используйте одну сборку, одинаковое время и отдельные каталоги результатов. Выполните каждую конфигурацию несколько раз и сохраните сравнительную таблицу: число выполнений, размер итогового корпуса. Кратко объясните различия.

2. **Переиспользование корпуса.** Если перед запуском в `out/` есть результаты предыдущего фаззинга, добавьте тестовые файлы из каталогов `queue` всех экземпляров фаззера во входной корпус, сохранив файлы с совпадающими именами. Минимизируйте объединённый корпус с помощью `afl-cmin` для собранной программы и используйте его для нового запуска. Предыдущий `out/` сохраните отдельно. В `summary.json` укажите число файлов до объединения, после него и после минимизации. Если предыдущих результатов нет, используйте исходный корпус.

3. **Остановка при отсутствии прироста покрытия.** Добавьте в конфигурацию `coverage_idle_seconds`, например `120`. Если покрытие не растёт в течение заданного времени, корректно завершите фаззинг и сохраните результаты. `duration_seconds` остаётся общим ограничением времени запуска; остановка происходит по первому из двух условий. В `summary.json` укажите причину остановки и время без прироста покрытия.

### Проверка и сдача

Запустите приложение на выбранной утилите из dast-1 без словаря и на выбранной утилите из dast-2 со словарём. Можно использовать подготовленные в лабораторных корпус и словарь. Для каждого варианта продемонстрируйте реализацию задания.

В PR должны находиться:

- исходный код приложения;
- README с установкой, запуском, номером варианта и описанием формата конфигурации;
- примеры конфигураций и исходников для проверки варианта;
- `submission/artifacts/` с отдельным каталогом для каждого запуска: начальный `input/`, использованный `dictionary.dict`, полный `out/`, `logs/build.txt`, скриншоты `screenshots/build.png` и `screenshots/fuzzing.png`, как в dast-1 и dast-2;
- `summary.json` в каталоге каждого запуска и результаты своего варианта.

Дополнительно, для получения бонусных баллов можно реализовать ещё один вариант или все, что звучит для вас интересно.
